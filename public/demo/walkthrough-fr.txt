Voici Slot, une application de réservation pour un coach sportif. Je vais te montrer le parcours d’un client, puis ce que voit le coach. J’ouvre une démonstration privée : les personnes sont fictives, mais les réservations passent réellement par le serveur et sa base de données.

Je choisis maintenant une séance disponible. À droite, le récapitulatif indique le jour, l’heure, la durée et le prix. Le fuseau horaire est affiché dans le calendrier. Cette étape permet de vérifier ce que l’on réserve avant de prendre une place.

Je réserve ma place. Elle est d’abord retenue temporairement, pendant dix minutes. Je confirme ensuite le paiement de démonstration : aucune carte n’est débitée. La réservation devient confirmée. Si le paiement était abandonné, cette retenue expirerait pour libérer la place.

Dans mes séances, je retrouve cette réservation. Je clique sur le bouton de déplacement, puis je choisis un autre horaire. Après confirmation, la réservation affiche la nouvelle heure. Ce changement vérifie à nouveau les disponibilités ; il ne se contente pas de modifier le texte à l’écran.

Je peux aussi annuler. L’application me demande de confirmer cette décision, puis affiche le statut annulé. La place redevient disponible. Les états sont donc explicites : en attente, confirmé ou annulé, avec une conséquence réelle sur la capacité du cours.

Je passe maintenant du côté du coach. Il retrouve son planning et les réservations dans le même espace. Les autorisations sont vérifiées par le serveur. Le changement de rôle que j’utilise ici est un outil de démonstration, pour découvrir les deux expériences rapidement.

Voici le test le plus intéressant : deux clients demandent simultanément la dernière place. Je lance les deux requêtes. Une seule est acceptée ; l’autre reçoit un refus propre. Ce résultat vient du véritable service de réservation. Cette capture utilise l’application locale, avec paiement simulé.
